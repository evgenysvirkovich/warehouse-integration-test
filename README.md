# Тестовое задание: Складская логика (FBS, Маркировка, Инвентаризация)

## Как запустить
Убедитесь, что у вас установлен PHP 8.1 или выше.
1. Поместите файлы данных (`catalog.csv`, `stock_cells.csv`, `fbs_tasks.json`, `scans.csv`, `inventory_count.csv`) в папку `data/`.
2. Выполните в терминале: `php run.php`

## Принятые архитектурные и логические решения

1. **Приоритезация заданий (Task A):** Задания сортируются по полю `ship_by` (ASC). Это гарантирует, что самые горячие заказы (с ближайшим дедлайном) забирают остатки первыми. Если товара не хватает, поздние задания помечаются как "невозможные к сборке".
2. **Оптимизация маршрута (Task A):** Итоговый лист подбора сортируется по адресу ячейки с использованием `strnatcmp` (естественная сортировка строк). Это гарантирует, что кладовщик будет двигаться по складу логично (A-01-01 → A-01-02 → A-02-01), а не прыгать хаотично.
3. **Валидация КИЗ (Task B):** Реализована строгая проверка по маске `^01(0\d{13})21(.+)$`. Скрипт проверяет не только наличие КИЗ у маркированных товаров, но и глобальную уникальность КИЗ across all tasks (ловит ситуацию, когда один и тот же код отсканирован в разных заданиях).
4. **Честная инвентаризация (Task C):** Ожидаемый факт рассчитывается как `Учётный остаток - Успешно собранные единицы`. Это предотвращает ложные недостачи, когда товар физически уже отсканирован для отгрузки, но ещё не списан из системы.

## Выводы по данным (результат работы скрипта)

- **Задание T-5003:** Невозможно собрать, так как товар `WH-2001` (остаток 1 шт.) был полностью изъят более срочным заданием `T-5001`.
- **Задание T-5002:** Недостача товара `WH-2010` (не отсканирован) и излишек `WH-2011` (отсканирован, но не был в задании).
- **Задание T-5003 и T-5001:** Обнаружен КРИТИЧЕСКИЙ дубль КИЗ `010200000000001521ABC123xyz0001`. Один и тот же код маркировки попытались использовать в двух разных заданиях.
- **Задание T-5004:** Ошибка валидации КИЗ. Для товара `2000000000022` отсканирован КИЗ, в котором зашит GTIN `02000000000015` (принадлежит товару `2000000000015`). Это подмена товара.
- **Инвентаризация:** Выявлена недостача по `2000000000046` (учёт 30, собрано 3, пересчёт 27 -> ОК, но в данных пересчёт 27, значит расхождений нет, а вот по `2000000000053` в ячейке A-02-01 учёт 0, а в B-02-03 учёт 15, при этом пересчёт показывает 0 и 15 соответственно, но есть пересорт по ячейкам).

## Рекомендации по улучшению процесса сборки (3-5 предложений)

1. **Валидация на краю (Edge Validation):** Проверка формата КИЗ и его уникальности должна происходить на стороне ТСД в момент сканирования (offline-словарь или мгновенный API-запрос), с запретом добавления скана в случае ошибки.
2. **Двухфазное резервирование:** При создании задания в WMS/1С остатки должны переходить в статус "Зарезервировано". Это исключит гонку данных (race condition), когда два кладовщика идут за последним товаром.
3. **Контроль "лишних" сканов:** Система должна блокировать завершение задания, если количество отсканированных единиц превышает заказанное, или если отсканирован товар, отсутствующий в спецификации задания.
4. **Разделение зон ответственности:** Внедрить обязательный этап "Контрольная сборка" (например, сканирование штрихкода уже заклеенной коробки), который сверяет итоговый состав с заданием перед передачей в зону отгрузки маркетплейса.
