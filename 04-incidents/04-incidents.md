# Разбор обращений сотрудников по логам

## inc1-b2b-500: B2B-сайт выдаёт «Server Error» после переноса базы

**Причина.** Laravel использует закэшированный файл конфигурации `bootstrap/cache/config.php`, который содержит старый хост базы данных `db-old.example.test`. После обновления `.env` с новым хостом `db-new.example.test` команда `php artisan config:clear` не была выполнена, поэтому приложение продолжает читать конфигурацию из кэша, игнорируя изменения в `.env`.

**Доказательства.**
1. `deploy.log` (21:41:02): `cp .env.new .env` — обновили файл с новыми параметрами БД.
2. `env_excerpt.txt`: `DB_HOST=db-new.example.test` — новый хост в `.env`.
3. `laravel.log` (21:41:07 и далее): `Host: db-old.example.test` — приложение пытается подключиться к старому хосту.
4. `ls_bootstrap_cache.txt`: `grep` показывает в `bootstrap/cache/config.php` строку `'host' => 'db-old.example.test'` — захардкоженный старый хост в кэше.
5. `laravel.log`: `SQLSTATE[HY000] [2002] Connection refused` — база недоступна по старому адресу.

**Что сделать сейчас.**
```bash
php artisan config:clear
php artisan config:cache
curl -I https://b2b.example.test
tail -f storage/logs/laravel.log | grep -i "connection"

**Как не допустить повторения.**
Добавить в CI/CD пайплайн обязательный шаг php artisan config:clear после обновления .env.
Внести в чек-лист деплоя пункт «Очистка кэша конфигурации при изменении переменных окружения».
Настроить мониторинг на ошибки SQLSTATE[HY000] [2002] с алертом в Slack/Telegram.
Документировать в runbook процесс переноса БД с явным указанием шага очистки кэша.
**Ответ сотруднику.**
 «Мы обновили настройки базы данных, но система использовала старые параметры из временного хранилища. Работа сайта восстановлена, сейчас всё работает корректно. Приносим извинения за неудобства.»

## inc2-hosting-503: Сайт периодически отвечает 503

**Причина.** В 9:00 и 9:15 одновременно запускаются три тяжёлых cron-задачи (`sync-prices`, `sync-stock`, `rebuild-catalog`), которые исчерпывают лимит Entry Processes (EP 20/20) на виртуальном хостинге LVE. Особенно ресурсоёмка задача `rebuild-catalog` (выполняется 240 секунд), которая блокирует все доступные PHP-процессы, из-за чего обычные запросы пользователей получают 503 ошибку.

**Доказательства.**
1. `crontab.txt`: в 9:00 ежедневно запускается `rebuild-catalog`, а каждые 15 минут — `sync-prices` и `sync-stock`.
2. `access.log` (09:00:00): все три задачи стартовали одновременно, `rebuild-catalog` выполнялся 240000ms (4 минуты).
3. `error.log`: множественные записи `[lsapi:error] Resource limit is reached: Entry processes limit (EP) 20/20` начиная с 09:00:03.
4. `access.log`: после 09:00 массовые 503 ошибки с `rt=1ms` (запросы даже не начали выполняться).
5. `lve_usage.csv`: в 09:00-09:03 `ep_used=20/20`, `cpu_percent=100`, `faults_ep=67-81`; в 09:15-09:16 снова пик (повторный запуск задач).

**Что сделать сейчас.**
```bash
# 1. Разнести запуск cron-задач по времени
# Изменить crontab:
# 0 9 * * * — rebuild-catalog
# 5 9 * * * — sync-prices
# 10 9 * * * — sync-stock

# 2. Проверить после изменений
tail -f /var/log/lve/stats.log
grep "503" access.log | wc -l

**Как не допустить повторения.**
Разнести тяжёлые cron-задачи по времени (минимум 5-10 минут между запусками).
Перенести rebuild-catalog на время минимальной нагрузки (например, 3:00 ночи).
Добавить мониторинг LVE-лимитов с алертом при EP > 15/20.
Оптимизировать rebuild-catalog: использовать очереди Laravel, кэширование, batch-обработку.
Рассмотреть апгрейд тарифа хостинга (больше EP лимит) или переход на VPS.
**Ответ сотруднику.**
 «Сайт выдаёт ошибку 503 из-за одновременного запуска нескольких тяжёлых задач обновления данных в 9:00 утра. Мы разнесём их выполнение по времени и перенесём самые ресурсоёмкие операции на ночные часы. Работа сайта стабилизируется в течение дня. Приносим извинения за неудобства.»

## inc3-exchange-1c: Заказы с сайта не попадают в 1С

**Причина.** Модуль обмена застрял на заказе ORD-B2B-7781 (job #88414) из-за ошибки «Контрагент не найден» в 1С. Новый клиент K-117 (UNP 190000000) был создан на сайте сегодня утром (07:51), но ещё не успел синхронизироваться с 1С. Worker пытается отправить заказ 190 раз (каждую минуту), но получает HTTP 422 и блокирует обработку всех последующих заказов в очереди.

**Доказательства.**

exchange.log (07:58:03): первая ошибка job #88414 ORD-B2B-7781 -> 1C HTTP 422: { "error ": "Контрагент не найден ", "unp ": "190000000 ", "client ": "K-117 "}.
exchange.log: далее job #88414 повторяется каждую минуту с attempt=2,3,4...190, next_retry=+60s.
queue_snapshot.txt: job #88414 имеет attempts=190, status=pending, created_at=2026-10-22 07:57:40.
queue_snapshot.txt: следующие заказы (#88415-#88421) имеют attempts=0 — они вообще не обрабатывались.
queue_snapshot.txt: клиент K-117 создан в 07:51:10, то есть за 7 минут до первой попытки обмена.
ticket.txt: бухгалтер обращается в 11:05 — к этому моменту очередь заблокирована уже более 3 часов.

**Что сделать сейчас.**

# 1. Пропустить проблемный заказ (переместить в failed или skip)
mysql -u b2b_app -p -e "UPDATE exchange_queue SET status='failed', error='Контрагент не найден в 1С, требует ручной синхронизации' WHERE id=88414"

# 2. Запустить worker для обработки накопившихся заказов
php artisan queue:work exchange --once

# 3. Проверить, что очередь разблокировалась
mysql -u b2b_app -p -e "SELECT COUNT(*) FROM exchange_queue WHERE status='pending'"

# 4. Вручную создать контрагента K-117 в 1С или запустить полную синхронизацию клиентов


**Как не допустить повторения.**

Реализовать skip-on-error стратегию: worker должен пропускать заказы с критическими ошибками (422) после N попыток (например, 5), логировать их в отдельную таблицу failed_jobs и продолжать обработку следующих.
Двусторонняя синхронизация клиентов: при создании нового клиента на сайте сразу запускать фоновую задачу на создание контрагента в 1С до того, как клиент оформит первый заказ.
Мониторинг очереди: алерт, если в очереди есть заказы с attempts > 10 или если последний успешный обмен был более 15 минут назад.
Разделение очередей: вынести синхронизацию клиентов в отдельную очередь clients-sync, которая выполняется перед exchange.

**Ответ сотруднику.**
«Обмен с 1С заблокирован из-за нового клиента, который ещё не создан в 1С. Мы пропустили проблемный заказ, все накопившиеся заказы будут отправлены в течение 10 минут. Клиента создадим в 1С вручную. Приносим извинения за неудобства.»

## inc4-retail-pos: Продажи магазина за день не появились в 1С

**Причина.** Из-за отключения электроэнергии и севшей батарейки BIOS/RTC на кассе POS-02 сбились системные часы на 01.01.2026. Касса закрыла и отправила смену №1188 с неверной датой. Модуль обмена получил данные, но отклонил их, так как дата документа (01.01.2026) попадает в закрытый для редактирования период в 1С (граница 01.10.2026).

**Доказательства.**

pos_sync.log: 2026-01-01 00:00:07 POS-02 boot: RTC battery low, system time not synchronized и все последующие операции этой смены датированы 2026-01-01.
exchange_retail.log: retail.WARNING: shop=2 shift=1188: 143 receipts skipped: document date 01.01.2026 is before 1C closed-period boundary 01.10.2026

**Что сделать сейчас.**

На кассе POS-02: заменить батарейку RTC, принудительно синхронизировать время (например, sudo ntpdate pool.ntp.org или через настройки ОС), убедиться, что время корректно.
В 1С: бухгалтеру/администратору 1С необходимо временно разрешить редактирование периода или создать документ ручной загрузки/корректировки с правильной датой (21.10.2026) для смены №1188, чтобы провести эти 143 чека.
Убедиться, что перед открытием новой смены время на POS-02 актуально.
**Как не допустить повторения.**

Настроить автоматическую синхронизацию времени (NTP) на всех POS-терминалах с запретом ручного изменения времени для пользователей.
Доработать POS-софт: при открытии смены сверять время с сервером; если разница > 5 минут, блокировать открытие и требовать вызова администратора.
Настроить алертинг в мониторинге: если в exchange_retail.log появляется запись skipped > 0, бот должен сразу отправлять уведомление в чат поддержки, а не просто писать WARNING.


**Ответ сотруднику.**

Причина в сбое времени на кассе №2 из-за отключения света: чеки за 21.10 ушли в систему с датой 1 января и были автоматически отклонены 1С как задним числом. Мы уже синхронизируем время на кассе и вручную загрузим эти продажи в 1С сегодня в течение часа.

**Чего не хватает для уверенного вывода:**
Я бы запросил конфиг NTP-клиента на POS-02 (например, cat /etc/systemd/timesyncd.conf или crontab -l), чтобы убедиться, что синхронизация не просто была настроена, но и действительно включена и не перезаписывается другими скриптами.

**Полезные команды для анализа (приложены):**

# Поиск ошибок синхронизации и пропущенных документов во всех логах
grep -iE "RTC battery low|skipped|closed-period" *.log

# Просмотр конкретных строк отклонения в логе обмена
awk '/WARNING.*skipped/ {print}' exchange_retail.log

## Приоритизация обращений (если бы они пришли одновременно)

Если бы все 4 инцидента поступили одновременно, я бы решал их в следующем порядке:

1. **inc1-b2b-500 (B2B-сайт не работает)**  
   **Почему первый:** Полная недоступность канала продаж для B2B-клиентов. Прямая потеря выручки. При этом время на восстановление (TTR) минимально: одна команда `php artisan config:clear` решает проблему за 10 секунд. Это классический "quick win", который мгновенно снимает критическое давление.

2. **inc3-exchange-1c (Заказы не попадают в 1С)**  
   **Почему второй:** Бизнес-процесс выполнения заказов полностью остановлен. Хотя данные не теряются (они в очереди), каждый час простоя увеличивает отставание склада и риск недовольства клиентов. Решение также относительно быстрое: пропустить один проблемный джоб и перезапустить воркер, что мгновенно разблокирует десятки накопившихся заказов.

3. **inc2-hosting-503 (Периодические ошибки 503)**  
   **Почему третий:** Проблема серьезная, но сайт не лежит полностью, а лишь "периодически" отвечает ошибками во время пиковых нагрузок cron-задач. Пользователи испытывают дискомфорт, но массового оттока или полной остановки продаж нет. Решение требует чуть больше времени (правка crontab, возможно, рестарт сервисов), поэтому беремся за него после устранения полных блокировок (п. 1 и 2).

4. **inc4-retail-pos (Продажи магазина не в 1С)**  
   **Почему четвертый:** Это проблема бухгалтерского учета и синхронизации, а не прямой остановки продаж. Деньги физически уже получены магазином, касса работает. Проблема затрагивает только один магазин за один день. Решение требует координации с физическим магазином (замена батарейки, настройка времени) и действий бухгалтера в 1С, что делает этот инцидент самым долгим по времени решения, но наименее критичным для бизнеса "прямо сейчас".
